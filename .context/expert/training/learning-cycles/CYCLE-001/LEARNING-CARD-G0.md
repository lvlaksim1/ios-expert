## 1. Проверенные первичные основания

1. Apple, *I/O Kit Fundamentals — The I/O Registry*: динамический реестр живых объектов; `IOService` и `IODeviceTree` — разные плоскости представления связей. Плоскость Device Tree отражает иерархию описания устройства, Service — отношения provider/client при работе IOKit. Наличие узла в первой плоскости не доказывает существования запущенного драйвера или диска во второй. Документ относится к историческому OS X, поэтому перенос на определённую версию iOS или виртуальную платформу требует независимой проверки: https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/TheRegistry/TheRegistry.html
2. Apple, *Driver and Device Matching*: классовый, пассивный и активный этапы сопоставления; свойства `IOProviderClass`, семейно-зависимые ключи личности драйвера, `probe` и оценка пригодности, затем `start`. Несовпадение одного семейно-значимого условия может исключить кандидата до `probe`, но точные правила нельзя выводить лишь из сходства строк `compatible`. https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/Matching/Matching.html
3. Apple, *The Base Classes*: `IOService` определяет жизненный цикл, отношения provider/client и публикацию; реестр содержит активные объекты, каталог драйверов — доступные описания. Наличие кода или личности драйвера в каталоге не является доказательством `probe`, `start` либо появления клиентского сервиса. https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/BaseClasses/BaseClasses.html
4. Apple, API `IOService::probe`: возвращает `IOService*` либо ноль, может менять `score`; при вызове кандидат уже прикреплён к provider. https://developer.apple.com/documentation/kernel/ioservice/1810605-probe
5. Apple, API `IOService::start`: вызывается для выбранного кандидата; возвращает `true` или `false`; неуспех ведёт к откреплению/освобождению экземпляра. https://developer.apple.com/documentation/kernel/ioservice/1811009-start
6. Apple, API `IOServiceGetMatchingService`: поиск зарегистрированных сервисов по словарю; для незарегистрированных объектов нужен иной способ обхода реестра. Следовательно, «не найден через matching API» не всегда равнозначно «никогда не существовал». https://developer.apple.com/documentation/iokit/1514535-ioservicegetmatchingservice
7. Apple, API `registerService` (kernel): публикация инициирует регистрацию, сопоставление обычно асинхронно. Сам факт вызова регистрации не доказывает завершение последующих этапов к моменту конкретного снимка. https://developer.apple.com/documentation/kernel/ioservice/1810726-registerservice
8. Apple, открытый исходный код XNU, **строго зафиксированная метка `xnu-10063.121.3`**, файл `iokit/Kernel/IOService.cpp`, Git blob `4903e7d75cb13c610c5ca15cf43184caff3bcebf`: `IOService::registerService` около строки 1031, `probe` около 762, `start` около 769, `probeCandidates` около 3830, вызов `inst->probe(this,&score)` около 4085, `startCandidate(inst)` около 4203. Эти строки подтверждают общий порядок именно **в указанном открытом снимке XNU**, а не внутренности любой iOS-сборки: https://github.com/apple-oss-distributions/xnu/blob/xnu-10063.121.3/iokit/Kernel/IOService.cpp

**Согласование источников:** историческая документация объясняет модель IOKit; код XNU подтверждает наличие основных переходов в конкретной версии. API DriverKit с `Start`/`RegisterService` и иными типами возврата нельзя механически смешивать с методами `IOService` ядра. Публичные документы не гарантируют совпадение закрытых драйверов, свойств и последовательности событий в конкретной iOS/эмуляторе.

## 2. Причинно-временная цепочка: что необходимо доказать

`Описание узла (IODeviceTree)` → `создан и опубликован provider (IOService)` → `найден кандидат по классу и свойствам личности` → `выполнен probe` → `успешен start` → `зарегистрированы требуемые дочерние сервисы, например хранилища` → `появились объект носителя и соответствующее BSD-устройство` → `верхние уровни смогли обнаружить тома`.

**Важно:** это **модель проверки**, а не обещание, что каждый драйвер проходит все этапы одинаково или что единственный драйвер напрямую создаёт `/dev/disk*`. Между контроллером и BSD-узлом могут быть дополнительные семейные сервисы, объекты носителя и механизмы публикации. Состояние `launchd`, APFS или пользовательского процесса является нижележащим следствием только после доказанной связи с данным устройством.

| Ступень | Положительное свидетельство | Чего оно ещё не доказывает |
| --- | --- | --- |
| Узел DeviceTree | Имя, путь, свойства и момент наблюдения в `IODeviceTree` | Публикацию provider в `IOService` |
| Provider | Устойчивый идентификатор записи, класс, родитель/клиенты и момент регистрации в Service-плоскости | Подходящую личность драйвера или его запуск |
| Пассивное сопоставление | Фактические ключи `IOProviderClass`, семейные ключи, значения в provider и правила семейства | Что `probe` действительно был вызван |
| `probe` | Журнал вызова и результат/оценка для **конкретного** кандидата | Успех `start` |
| `start` | Вызов, provider, код результата и временная отметка | Регистрацию всех зависимых сервисов и `/dev/disk*` |
| Сервис носителя | Реальная запись семейства хранения, связи с контроллером, признаки публикации | BSD-имя в нужной среде |
| BSD-устройство | Гостевой `/dev/disk*` и соответствие объекту носителя | Успех APFS/монтирования/системного запуска |

## 3. Алгоритм локализации первого доказанного разрыва

1. **Зафиксировать происхождение каждого фрагмента.** Указать `boot_id` (если доступен), сборку ОС/ядра, физическую или виртуальную среду, источник журнала, часы/смещение и интервалы неопределённости. Не объединять разновременные снимки в одну мгновенную картину.
2. **Упорядочить события** `t0, t1, …` внутри одной доказанной загрузки. Если часы разных журналов несопоставимы, отметить частичный порядок, а не выдумывать точные секунды.
3. **Сверить две плоскости независимо.** Узел `IODeviceTree` и объект `IOService` не взаимозаменяемы. Связывать их по проверяемым идентификаторам, пути, свойствам и отношениям, не только по похожему имени.
4. **Проверить provider.** Есть ли опубликованный provider нужного класса? Если его не наблюдали, отделить «отсутствует в снимке» от «никогда не публиковался». Учитывать асинхронность и возможное удаление.
5. **Проверить кандидатные личности.** Сопоставить `IOProviderClass`, свойства и семейно-зависимые правила. Строка `compatible` может быть значимой, но без подтверждения конкретного алгоритма нельзя утверждать, что именно она исключила кандидата. Наличие двоичного кода не означает прохождения пассивного сопоставления.
6. **Проверить активную фазу.** Отдельно искать факт вызова `probe`, его результат и порядок кандидатов. Если журнал явно фиксирует отклонение, это может быть первым доказанным сбоем; если только отсутствует запись — это пока пробел наблюдения.
7. **Проверить `start`.** Подтвердить результат запуска и ресурсные причины лишь при наличии фактических диагностических сообщений. Успешный `probe` не доказывает успешный `start`. Неуспех `start` не доказывает единственную первопричину, пока нет данных об источнике ошибки.
8. **Проверить дальнейшую публикацию.** Есть ли дочерние сервисы, объект носителя, BSD-имя именно в исследуемом госте? Отсутствие `/dev/disk*` — наблюдаемый симптом, но само по себе не локализует проблему между сопоставлением, запуском и публикацией.
9. **Сформулировать ровно один первый доказанный разрыв** в виде: «между подтверждённым событием X в момент/интервал T и ожидаемым Y отсутствует подтверждение; если журнал явно сообщает отказ Z, первым доказанным отказом является Z». Если причинный разрыв не локализован — написать `НЕ УСТАНОВЛЕН`.
10. **Назначить минимальное следующее наблюдение, только чтение.** Запросить недостающий срез Service-плоскости, соответствующую личность, диагностическую запись `probe/start`, карту provider/client или гостевую запись носителя. Никаких изменений прошивки, драйвера, настройки защиты или установки ПО в рамках этой учебной пробы.

## 4. Контроль временных срезов и отрицательных свидетельств

Минимальная форма журнала:

| Поле | Обязательное значение |
| --- | --- |
| `case/boot_id` | Идентификатор единственной загрузки либо `UNKNOWN` |
| `environment/build` | Устройство/гость, ОС, ядро, версия исходников (если известны) |
| `source/plane` | Журнал, `IODeviceTree`, `IOService`, BSD либо другой конкретный источник |
| `observed_at` | Время, точность, источник часов |
| `entry/provider/personality` | Устойчивые идентификаторы и свойства, либо `UNKNOWN` |
| `phase/outcome` | `DISCOVERED`, `PUBLISHED`, `MATCHED`, `PROBED`, `STARTED`, `MEDIA_VISIBLE` — только при прямом свидетельстве |
| `confidence` | `FACT`, `HYPOTHESIS`, `UNKNOWN` с указанием основания |

Различать:
- **`NO_EVENT_IN_CAPTURE`** — событие не встретилось в данном журнале/интервале; не доказано, что оно не происходило.
- **`EVENT_FAILED_EXPLICITLY`** — есть явная запись ошибки с привязкой к объекту и времени.
- **`NOT_YET_OBSERVED`** — на снимке `t1` нет объекта, который может появиться на `t2`.
- **`OBSERVED_THEN_GONE`** — объект был и исчез; требуется установить причину удаления.
- **`DIFFERENT_BOOT_OR_BUILD`** — сравнение не доказывает переход внутри одного выполнения.

Снимок после запуска не равен истории всего запуска; «не найдено» не равнозначно «не вызывалось». `registerService` может инициировать асинхронное сопоставление. Протокол должен сохранять временную точность и область наблюдения.

## 5. Воспроизводимая последовательность только чтением

**Если это macOS и инструменты доступны в разрешённой среде:** допустимые примеры наблюдений `ioreg -p IODeviceTree -l -w0`, `ioreg -p IOService -l -w0`, выборочные `ioreg -p IOService -r -c <Class> -l`, просмотр уже существующих системных журналов и `diskutil list`. Эти команды иллюстрируют способ получения сведений **на соответствующем хосте**, а не свидетельствуют о гостевой iOS. Наличие `diskutil` на хосте не доказывает наличие диска в госте.

**Если это iOS, исследовательский образ или эмулятор:** использовать только реально доступные и разрешённые снимки гостевого I/O Registry, журналы загрузки и гостевую таблицу устройств; если доступа нет — честно отметить `UNKNOWN`. Не выдавать недоступный `ioreg` за выполненный. Не изменять образ ради получения данных.

Сопоставлять снимки одного объекта на `t0/t1/t2` по идентификаторам, а не по порядку строк. В итоговом диагнозе обязательно указать источник каждого вывода, первый явный отказ (если он есть), одну ближайшую проверку только чтением и границу доказательств.

## 6. Ограничения и проверка исполнения

**FACTS:** проверенная документация Apple описывает разные плоскости I/O Registry, три фазы сопоставления, `probe`, `start`, `registerService`; конкретная версия XNU подтверждает вызовы `probe` и `startCandidate`. **HYPOTHESES:** несовпадение свойств, отложенное сопоставление, ошибка выделения ресурсов или отсутствие публикации — возможные объяснения лишь при подтверждающих журналах. **UNKNOWN:** конкретные правила закрытого драйвера, поведение конкретной сборки iOS, виртуального оборудования, точные времена и первопричина без входных диагностических данных.

**RULE_KNOWN:** анализ только чтением; отделение фактов от гипотез; замороженная рубрика и входные задания; раздельные запуски PRETEST/LEARN/POSTTEST/EVALUATE; паузы >=5 секунд между запросами; отсутствие изменений G/D. **RULE_APPLIED:** прочитан только PLAN.md; наличие PRETEST-RESULT подтверждено по имени и SHA без чтения ответа; POSTTEST и результаты оценки не открывались; использованы первичные источники и зафиксированная версия XNU; никаких изменений драйверов, прошивки или настроек. **COMPLIANCE_CHECKED:** задача LEARN ограничена учебной карточкой, оценка не выполнялась, дальнейший POSTTEST остаётся отдельным запуском; никакие данные реального устройства не были исследованы.

**Статус:** `LEARN_MATERIAL_PREPARED`; G0 — учебная карточка-кандидат, **не подтверждённая квалификация**. Следующий независимый этап — POSTTEST; разница результатов двух синтетических задач сама по себе не доказывает причинное действие обучения.
